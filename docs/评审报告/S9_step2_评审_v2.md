## 二、新缺陷

### N1【中，必须修】欧式价格写法被静默解析成错的数（−0.5）

- 位置：
  - `backend/fba_tool/lingxing_adapter.py:40`（parse_price 无条件删掉所有逗号）
  - 影响 `lingxing_preview.py:302-305`（_num_or_none）、`lingxing_sync.py:217-222`（_price_or_none）、`product_import.py:85`（Excel 导入），三处共用
  - `product_fields.py:272`（_valid_price）也删逗号
- 实测结果：

  | 输入 | 解析结果 | 说明 |
  |---|---|---|
  | "12,5" | 125.00 | 放大 10 倍 |
  | "1.299,00" | 1.30 | 缩小约 1000 倍；_valid_price 给 1.299 |
  | "$1,2" | 12 | |
  | "1,2,3" | 123 | |

  "1 299,00" 和 "¥12" 返回 None，正确。
- 后果：
  - 预览、定时同步、Excel 导入都会写入错价，而且没有任何提示。
  - 例：本地 15/18，领星售价 "12,5"，定时同步后售价 125，申报价 125，报关包单价 125。
  - 例："1.299,00" 写成售价 1.30，因促销判断申报成了常规价 18。
  - 用户这次明确要求“不能把欧式写法误解析成错的数”，没有做到。
- 复现：
  - `%TEMP%\fba_review_s9s2fix\p4_m4.py`（A3 解析表）
  - `t_a3_edge.py::test_sync_path[12,5]`、`test_import_path[12,5]`
  - 接口复现 `imp.py`：POST `/api/master-data/import/listing/preview` 上传 "12,5"，返回 200，new=125.0
- 修复建议：
  - 逗号只在标准千分位格式下删除：`^\d{1,3}(,\d{3})+(\.\d+)?$`。
  - 出现 "数字,1~2 位数字" 结尾，或同时有 "." 和 ","、且 "," 在后，判为无效，返回 None 并提示“疑似欧式写法”。不要猜。
  - 补测试："12,5"、"1.299,00"、"$1,2"、"1,2,3" 都应返回 None，或者明确报错。

### N2【中，必须修】超大数抛 InvalidOperation，整次同步失败，导入接口 500（−0.3）

- 位置：
  - `lingxing_adapter.py:48`：`d.quantize(Decimal("0.01"))` 遇到超过 28 位精度的数抛 InvalidOperation。
  - parse_price 自身不捕获。`_num_or_none` / `_price_or_none` 有包一层，但 `lingxing_adapter.py:87`（map_listing_row）和 `product_import.py:85` 直接调用。
  - `routers/master_data.py:246-249`：_import_call 只捕获 ValueError，而 InvalidOperation 不是 ValueError。
- 实测结果：
  - **同步**：领星某一行售价为 "1e30" 或 40 位 9 时，map_listing_row 抛异常，整次 Listing 同步中止。
    - 手动同步：报错事件 fatal=False，提示原样露出 `[<class 'decimal.InvalidOperation'>]`。
    - 定时同步：重试 4 次后仍失败。
    - 结果：一条脏数据挡住所有 SKU 的同步。
  - **导入**：Excel 导入价格 "1e30"，接口返回 **HTTP 500**。
  - **无上限**："1e20" 被当成合法售价写入，申报价也是 1e20。探针里这个 SKU 的报关包没有生成明细行（取第 1 行时 IndexError；原因未再追，记为未测细节）。
- 复现：
  - `t_a3_edge.py::test_sync_path[1e30]`、`test_sync_path[999…9]`、`test_import_path[1e30]`、`test_sync_path[1e20]`
  - `imp.py`（1e30 → 500）
- 修复建议：
  - parse_price 内部把 quantize 包进 try，异常返回 None。
  - 加合理上限（比如 >100000 判为无效并提示）。
  - map_listing_row 单行价格失败时，只让该字段为空，不中止整批。
  - _import_call 同时捕获 ArithmeticError，或在 parse_price 内部根治。
  - 补测试：1e30、40 位 9、1e20。

### N3【轻】极小正数被四舍五入成 0.0（−0.1）

- 位置：`lingxing_adapter.py:46-48`。先判断 `d <= 0`，后 quantize，于是 "1e-3"、"0.004" 得到 0.0。
- 后果：
  - Excel 导入把 listing_price=0.0 写入，也不报错，绕过了“必须大于 0”的提示。申报端 `_valid_price` 会把 0 当作无售价，所以不会报出 0 价。
  - 领星同步路径会被预览识别为无效，但提示写的是“无效（0.0）”，不是原始值 "1e-3"（`lingxing_preview.py:343`）。
- 修复建议：quantize 之后再判断 `<= 0`。提示显示领星的原始值。

### N4【轻】UI（逐条见 §三·UI，−0.5）

成立的有 (a)(b)(c)(e)(f)，外加 (g) 的 5.0% 显示问题。

### N5【轻】403 带限流语义也被当鉴权，不再重试（−0.1）

- 位置：
  - `lingxing_mcp_client.py:80`（AUTH_CODES 含 403）
  - `:100`（信封）
  - `:166`（JSON-RPC）
  - `:453`（HTTP 403）
- 实测结果：
  - HTTP 403 "rate limit"、信封 403 "请求过于频繁"、JSON-RPC 403 "Too many requests"，search 和 action 两个阶段都判为 LingxingAuthError，fatal=True。
  - 定时同步 run_once 只试 1 次。
  - 429 / 5xx / 超时 / 非 JSON / 空 SSE 都重试 3 次，正确。
- 后果：领星如果用 403 表示限流，就会被当成 Key 失效直接放弃，要等下一个周期。按开发方规格这是“设计如此”，但用户点名要求看这一点，所以只记轻微。
- 修复建议：403 文字含“频繁 / 限流 / rate / too many”时按可重试处理；401 保持不重试。

### N6【轻】JSON-RPC 分支只凭文字就判鉴权，与注释和 isError 规则不一致（−0.1）

- 位置：`lingxing_mcp_client.py:166`，条件是 `ecode in AUTH_CODES or _is_auth_text(msg)`。注释（`:78-79`）写的是“文字只和结构化信号一起用”。
- 实测结果：
  - JSON-RPC −32000、文字含“Key无效” → 鉴权，不重试。
  - 不带 code、文字含“Key 无效”（有空格） → 鉴权。
  - 同样的限流文字放在 isError 里（不以鉴权原文开头）→ 可重试。
  - 同样的限流文字放在信封 429 里 → 可重试。
- 修复建议：二选一，然后把注释和规格对齐：
  - JSON-RPC 只在 code 为 401/403，或文字以领星鉴权原文开头时判鉴权；
  - 或者在文档里写明 JSON-RPC 按文字判。
