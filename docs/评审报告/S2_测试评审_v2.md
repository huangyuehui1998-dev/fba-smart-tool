## 二、新规则

### 2.1 实际行为（逐级测了回落）

`resolve_declared_price` 的结果：

| 情况 | 结果 |
|---|---|
| 有领星 listing_price，同时有手填价 29.99 | 用 15.99，来源 lingxing（领星价压过手填价） |
| 没有领星 listing_price，只有手填 | 用手填 29.99，来源 manual |
| 领星只有 price 兜底，同时有手填 | 用手填（手填 > price 兜底，符合新规则） |
| 只有领星 price | 14.0，来源 `lingxing_price` |
| 只有 landed_price | 13.0，来源 `lingxing_landed_price` |
| 只有旧 declared_value | 29.99，来源 legacy |
| 什么都没有 | None |

**用 test1 第一票做的端到端测试**：5 个 SKU 分别设成 5 种情况，然后生成报关数据并导出。

- 出现的提示：
  - `price_legacy`：“申报价来自旧数据，未经领星核实…”
  - `price_missing`：“…没有申报价，不能导出”
  - `price_drop`：“领星实时售价比历史申报价低很多：…（29.99 → 15.99）”
- 有 SKU 缺价时，导出报 `CustomsExportBlocked: 缺申报价…`，路由返回 422；补上价格后导出正常。
- **说明**：422 是在函数层面加读路由代码 L83 确认的，没有通过 HTTP 请求实际调用 `/api/customs/export`。

### 2.2 书面依据 → 【待用户确认】

- **“领星 listing_price > 手填”这条，只在 HANDOFF 第 7 节和代码注释里写了“用户 2026-10-16 定”。** /workspace 下的答案文件、方案、规则清单里，都没有对应的用户原话或确认记录。
- 现有文档仍是旧口径（手填优先）：
  - 方案 L92：“`declared_value` 仍可手填覆盖（Q4 规则不变）”；
  - 方案 L150：手填优先、回落售价并警告；
  - 规则清单 L68、L233（“优先级高于售价”）、L292；
  - `待确认问题_初版答案.md` L45（Q4 选 B）。
- v8 E1 只写了“申报价 = 实时售价，以领星为准”，**没写手填值是否还能覆盖**。所以“领星压过手填”既可以理解成对 E1 的延伸，也可能和 Q4 冲突，必须由你本人确认。
- **“Listing 以 MCP 为主、文件备用”**也没有书面依据。方案 L40 写的是首期以文件手动导入为准，L83 写的是“S5：MCP 定时同步，用户同意接入后启用，默认关闭”。

### 2.3 golden 口径没有同步
- `tests/golden/README.md` L5 和 `invoice_manifest.csv` 里 13 条的 expected_warnings 仍写 `DECLARED_VALUE_FALLBACK`，前提是“快照 declared_value 为空 → 回落售价并警告”。
- 按新规则，有领星价时来源就是 lingxing，不会再出这个“回落”警告，所以这个期望值已经过时了。
- 本轮 `tests/golden` 目录 0 处修改，S3 跑 golden 时会对不上。

### 2.4 和“手填值锁定”是否冲突
- 除申报价外，其他手填字段仍然锁定（见 6c）。只有申报价的取值顺序不受锁定约束（领星价优先），HANDOFF 第 7 节写明了这一点。
- **提示不完整**：手填价被领星价压过时，只有领星价比手填价低 20% 以上才会出 `price_drop` 提示。领星价更高，或者降幅在 20% 以内时，不会有任何提示，手填价就这样被静默替换了。
  - 依据：`customs_package.py` 里的 `price_checks` 只判断降幅；我用 29.99 → 15.99 这一组实测确认了会提示。
  - 建议：只要手填价没被采用，就加一条“手填申报价 X 未采用，按领星售价 Y”的提示。
